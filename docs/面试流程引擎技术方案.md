## 1. 当前架构概述

项目已实现基于 LangGraph StateGraph 的完整面试 Agent，包含 13 个确定性节点，
支持 PostgreSQL Checkpointer 中断/恢复、多角色 Persona 驱动、证据提取评分、SSE 事件流。

Graph 节点链：
hydrate_context -> research_context -> build_interview_plan -> select_question
-> wait_for_input -> guard_input -> extract_evidence -> decide_followup
-> interviewer_respond -> score_question -> advance_stage -> finalize_report

wait_for_input 使用 interrupt()，恢复只传 inputId 不进 checkpoint。
guard_input 处理空值/重复/注入/超长拦截。
decide_followup 用代码规则决定追问/评分。

具体实现以 `api-server/src/modules/interview-agent/` 下的图、服务与测试为准。

## 3. 核心增强模块

### 3.1 关键词深挖（OfferNow Round 2）

现有问题：assessAnswerSufficiency() 只检查格式（有无数字、有无结果词），不提取技术名词。

改动：answer-sufficiency.ts 新增 extractKeywords() 纯函数。

正则匹配规则（按优先级）：
1. 大写字母+数字组合：BGE-M3, GPT-4o, CNN-BiLSTM
2. 2-6 个大写字母缩写：RAG, FAISS, ASR, NER
3. 常见框架/项目名：React, Redis, Docker, PostgreSQL
4. 技术术语：Transformer, Embedding, Fine-tuning

输出：最多 5 个去重关键词，短回答（<20 字）返回空。

关键设计：纯函数，无状态无 IO。在 guard_input 之后、decide_followup 之前调用。
结果写入 AgentGraphState 的 coveredDimensions（复用现有字段）。

### 3.2 含糊检测 + 压力测试（OfferNow Round 3）

现有问题：AnswerEvidenceGap 只有 4 种，无"含糊"检测。

改动：

1. interview-agent.types.ts 的 AnswerEvidenceGap 新增 "vague"
2. answer-sufficiency.ts 新增 detectVagueSignal() 和 buildVagueFollowUp()

detectVagueSignal 检测模式：
- "做了优化/改进/调整" 但不具体说怎么做
- "效果不错/挺好/满意" 无量化指标
- "用了相关/一些/某些技术" 避而不谈
- "等等/之类的/诸如此类" 列举不完整

buildVagueFollowUp 模板（按关键词有无分支）：
- 有关键词 -> 方案对比追问：为什么选 X 而不是 Y？X 对比 Y 优缺点？
- 无关键词 -> 举例催促：能否用一个具体例子说明？

### 3.3 内容阶段感知（GPTInterviewer 阶段概念）

现有问题：AgentPhase 是运行时阶段（preparing/awaiting_answer/scoring），
不是面试内容阶段。rolePlan 用技术/主管/HR 角色驱动题序，但无内容语义。

改动：roles/personas.ts 的 RolePersona 新增字段。不改变 AgentPhase。

新增类型：
ContentPhase = "introduction" | "tech_fundamentals" | "project_deep_dive" | "system_design" | "wrap_up"

各角色权重配置（使用 contentPhaseWeights 按比例分配该角色的题目数）：

```
general:
  introduction:       1 题  (约 20% / 权重 10)
  tech_fundamentals:  1 题  (约 20% / 权重 15)
  project_deep_dive:  2 题  (约 40% / 权重 45) <- 项目深挖占比最高
  system_design:      1 题  (约 20% / 权重 20)
  wrap_up:            0 题  (过渡不计入题量 / 权重 10)

technical:
  tech_fundamentals:  1 题  (约 25%)
  project_deep_dive:  2 题  (约 50%) <- 技术面试官一半题量用于项目深挖
  system_design:      1 题  (约 25%)

manager:
  project_deep_dive:  2 题  (约 65%)
  system_design:      1 题  (约 35%)

hr:
  wrap_up:            1 题  (100%)
```

权重配置通过以下方式与现有 capability-blueprint.ts 协作：
- capability-blueprint.ts 按能力维度分配每道题的主维度（COMMUNICATION / TECH_DEPTH 等）
- contentPhaseWeights 在上述维度之外增加一道"题的内容属性"层，决定追问风格和 transition
- 两者的交叉决定了每道题的最终风格：例如"同是 TECH_DEPTH 维度的题，在 tech_fundamentals 阶段偏理论，在 project_deep_dive 阶段偏项目实战"。
- 运行时代码根据 rolePlan 的角色顺序 + contentPhaseWeights 计算当前题属于哪个内容阶段，计算结果写入 SSE 的 agent.question_ready 事件。

不改变现有 capability-blueprint.ts 的分维逻辑。

### 3.4 decide_followup 增强后的判定流程

decideFollowUp(state):
  if followUpCount >= 3 -> score（现有逻辑）
  if detectVagueSignal(answer) -> follow_up（新增：压力测试）
  if extractKeywords(answer) has results -> follow_up（新增：关键词深挖）
  if !assessAnswerSufficiency(answer) -> follow_up（现有逻辑）
  else -> score（现有逻辑）

## 7. 测试策略

### 单元测试

extractKeywords 测试：
- 含技术名词的回答应提取到关键词（BGE-M3, FAISS, Redis）
- 最多返回 5 个关键词
- 短回答返回空数组

detectVagueSignal 测试：
- "做了优化" 应检测到含糊
- 含具体数字的描述不应误报

buildVagueFollowUp 测试：
- 有关键词时生成含对比词的追问
- 无关键词时生成"举例子"催促

### 集成测试

- 含糊回答触发 stress 追问分支
- 技术名词回答触发 deep_dive 追问分支
- 角色切换时 contentPhase 值正确

---

## 8. 边界情况

- 回答全是技术名词无完整句子：关键词提取到，但充分度检测返回 missing_action -> 追问补充行动
- 连续含糊：followUpCount 到 3 强制进入评分
- 重复关键词在多个追问中出现：coveredDimensions 去重，prompt 指示 AI 不重复追问
- 角色只有 1 题：contentPhase 取该角色 contentPhases[0]
- 无简历：自动跳过 project_deep_dive 阶段，contentPhase 序列不含它
