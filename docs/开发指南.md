# 开发指南

> 状态：当前｜维护者：开发团队｜最后核验：2026-07-16｜代码基线：`main@6958ac3`｜事实源：package scripts、目录结构、AGENTS 规则与构建配置

## 1. 环境要求

- Node.js：所有 workspace 统一要求 `>=22`。
- npm：使用仓库根目录唯一的 `package-lock.json`。
- 可选：Rust/Tauri 2、Supabase CLI、PostgreSQL。
- Windows PowerShell 用于现有本地基础设施和 Tauri 脚本。

## 2. 安装与配置

```powershell
npm install
Copy-Item .env.example .env
```

只填写当前开发所需变量。`VITE_*` 会进入客户端；服务角色、数据库、模型、语音和加密密钥禁止使用 `VITE_` 前缀。API 通过 `apps/api/src/preload.ts` 读取仓库根 `.env`。

## 3. 本地启动

```powershell
# 终端 1：Web http://localhost:3000
npm run dev

# 终端 2：API http://localhost:3001
npm run api:dev
```

常用命令：

```powershell
npm test
npm run lint
npm run build
npm run build:native:dev
npm run verify:native
npm run tauri:dev
npm run build:api
```

Checkpoint 集成测试只允许使用显式 `AGENT_TEST_DATABASE_URL`，不得借用生产 `DATABASE_URL`。

## 4. 目录和模块规范

后端新功能创建独立 `apps/api/src/modules/<feature>/`，至少包含 routes/service/repository/schemas；前端新功能创建独立 `apps/web/src/features/<feature>/`，包含 API、类型、Hooks 和组件。

- Route：认证、输入校验、调用和错误映射。
- Service：业务流程、不变量、幂等、并发和 fallback。
- Repository：数据库/RPC、所有权和字段映射。
- `apps/web/src/routes/*.tsx`：只做 `createFileRoute` 和页面壳。
- 新后端路由必须挂载到 `apps/api/src/app.ts`。
- 禁止手工编辑 `apps/web/src/routeTree.gen.ts`。

## 5. 编码规范

- TypeScript、ESM、2 空格、Prettier。
- 数据库字段 snake_case，API/前端 camelCase，UI 文案中文。
- 每个代码文件一行职责注释；函数/方法使用 JSDoc；类型字段说明用途。
- 注释解释职责、原因、边界和 fallback，不翻译代码。
- Prompt 构建函数说明输入影响、信任边界和严格响应格式。
- Repository 注释说明 select/join、RLS、RPC 和 fallback 策略。
- 禁止无编号/责任人的 TODO 和裸 `console.*`。

## 6. 功能开发流程

1. 阅读根 `README.md`、`AGENTS.md` 及任务相关文档。
2. 检查 `git status`，识别并保护他人未提交改动。
3. 从现有 routes/schema/repository/migration 建立事实基线。
4. 先定义请求、响应、状态和失败行为，再实现模块。
5. 同步更新 API、数据、安全、测试和变更日志。
6. 运行按风险选择的测试、Lint、构建和 `git diff --check`。
7. 只暂存本任务文件，使用 Conventional Commits 中文描述。

## 7. 代码审查清单

- 行为是否满足对应 `FR-*`/`AC-*`，是否遗漏空白、超长和权限错误。
- Route/Service/Repository 边界是否清楚，是否把另一功能域塞入现有模块。
- 是否审查幂等、并发 claim、重复请求、刷新、失败和恢复。
- 数据查询是否限制用户所有权，RLS/RPC 是否提供第二道边界。
- 模型、网页、文件和用户输入是否经过 schema、长度和证据校验。
- Checkpoint/event/log 是否包含正文、凭据或思维链。
- 错误是否安全、可操作且可观测，是否泄露内部实现。
- 测试是否覆盖成功、拒绝、并发、恢复和依赖失败。
- 文档、OpenAPI、迁移和变更日志是否同步。

## 8. Git 规范

提交格式：`<type>(<scope>): <中文描述>`，类型使用 `feat`、`fix`、`refactor`、`docs`、`db`、`config`、`test`。一次提交只做一件事，首行不超过 72 字。

禁止无授权执行 `reset --hard`、`clean -fd`、强推、部署、生产数据库写入或迁移历史修复。

## 9. AI 与新成员接手

- 先读根目录 [README](../README.md) 的文档中心和 [AGENTS](../AGENTS.md) 协作规则。
- 优先执行只读检查，确认分支、远程、最新提交和未提交改动。
- 文档与代码冲突时，以代码为准，并在同一变更修正文档。
- 不把猜测写成现状，不虚构测试、人工 Review、性能或生产结果。
- 未经明确授权不推送、部署、发送外部消息或操作生产资源。

## 10. 完成定义

实现、类型、schema、错误、日志、测试、文档和迁移保持一致；相关验证通过；未覆盖的风险明确记录在路线图，而不是隐藏在 TODO 或聊天记录中。
