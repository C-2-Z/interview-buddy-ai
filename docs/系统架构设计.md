# 系统架构设计

> 状态：当前｜维护者：架构与开发团队｜最后核验：2026-07-16｜代码基线：`main@6958ac3`｜事实源：`apps/web/src/`、`apps/api/src/app.ts`、当前 modules、migrations 与部署配置

## 1. 架构目标

- 支持文字辅导与语音模拟两条产品链路，共享统一 Agent 业务状态。
- 以业务表作为事实源，允许刷新、断线、重试和服务重启后恢复。
- 隔离浏览器、API、数据库、AI Provider、网页资料和 Native 容器的信任边界。
- 通过模块化结构控制功能耦合，通过契约和自动化测试抑制文档漂移。

## 2. 系统上下文

```text
用户
 ├─ Web SSR / Browser
 └─ Native SPA / Tauri WebView
          │ HTTPS / SSE / WSS
          ▼
      Hono API
       ├─ Supabase Auth + PostgreSQL + RLS/RPC
       ├─ LangGraph + Postgres Checkpoint
       ├─ DeepSeek / OpenAI / Anthropic compatible chat
       ├─ Qwen Realtime ASR/TTS
       └─ Tavily / Wikimedia 等受控公开资料源
```

浏览器和 Native 客户端都是不可信客户端；服务端必须独立完成认证、输入校验、所有权判断和敏感数据处理。

## 3. 容器与职责

### 3.1 前端与 SSR

- `apps/web/src/routes/`：TanStack 文件路由薄入口。
- `apps/web/src/features/`：业务 feature、组件、Hooks、API 和类型。
- `apps/web/src/shared/`：HTTP、运行时配置、平台适配和共享能力。
- TanStack Query 管理服务端状态；Supabase 客户端管理认证会话。
- SSR 只使用公开配置；服务端密钥不得进入客户端 Bundle。

### 3.2 API

- `apps/api/src/app.ts` 是 HTTP 路由注册事实源。
- 每个功能域独立拥有 routes/service/repository/schemas。
- `serve.ts` 启动 Node HTTP，并安装 `/api/voice/ws` WebSocket。
- 全局处理 CORS、统一错误映射和带模块标签的 consola 日志。

### 3.3 数据与认证

- Supabase Auth 颁发用户身份。
- PostgreSQL 业务表保存会话、问题、消息、评分、报告、活动和用户资源。
- RLS 与 RPC 负责数据库边界；Service/Repository 仍需显式传递用户身份。
- LangGraph Checkpoint 使用独立 schema，只保存恢复所需的最小状态。

### 3.4 AI 与外部服务

- 文本模型通过用户设置和服务端 Provider 适配层调用。
- Qwen Realtime 提供 ASR/TTS，不负责决定业务状态推进。
- 网页研究结果属于不可信证据，必须经过超时、大小、来源和内容约束。
- 知识库通过文档解析、分块、嵌入、检索、压缩和引用完成 RAG。

## 4. 状态边界

| 状态                             | 事实源               | 不得承担的职责                           |
| -------------------------------- | -------------------- | ---------------------------------------- |
| 面试会话、问题、回答、评分、报告 | 业务表               | 不得只存在内存或 Checkpoint              |
| Graph 执行位置和可恢复控制状态   | Postgres Checkpoint  | 不保存回答、简历、网页全文、凭据或思维链 |
| SSE 增量重放                     | `agent_events`       | 不作为完整业务记录                       |
| 前端缓存                         | React Query/组件状态 | 不决定最终业务状态                       |
| 语音连接状态                     | WebSocket 会话       | 断线不得丢失已确认的业务提交             |

## 5. 关键数据流

### 5.1 创建会话

客户端提交配置 → readiness 校验 → 认证与 schema 校验 → 创建冻结会话配置 → 独立准备工作流加载 Skill/简历摘要、生成角色计划与代码 baseline、可选增强策略、轮换选出首题 → Graph 运行到输入 interrupt → 原子提交策略、首题、事件和业务投影。题库候选是正常主链，只有严格角色、难度和主维度下候选为零时才允许模型补题。

新会话内部运行时为 `agent-v3-interactive-v2`，有效 Graph 只保留真实执行节点：

```text
hydrate_context -> wait_for_input -> guard_input -> decide_response
  -> interviewer_respond -> wait_for_input
  -> score_question -> reflect_strategy -> advance_stage
     -> select_question -> wait_for_input
     -> finalize_report -> update_training_memory
```

规划、授权工具、工具执行和首题准备不伪装为 Graph 空节点；`score_question` 负责证据提取、校验、评分和原子提交。旧会话缺少 `graphVersion` 时继续使用既有 Graph 和 `agent-v3` namespace，新会话使用独立 `agent-v3-interactive-v2` namespace。

### 5.2 提交文字输入

输入校验 → `inputId` 幂等检查 → 并发 claim → 保存回答 → Graph 追问/评分/选题 → 原子推进业务状态 → 写最小事件 → SSE/工作区投影。模型失败时 operation 保留稳定错误码和原回答；`/retry` 复用原 `inputId` 与 checkpoint 从失败节点继续，不重复写回答、评分、事件或题目。

### 5.3 语音输入

HTTP 签发短期 WebSocket token → `/api/voice/ws` 验证用户和会话 → 音频送 ASR → 最终文本进入同一 Agent 输入流程 → 业务事件驱动 TTS → 客户端播放和打断。

### 5.4 知识库

上传/文本 → 文件与所有权校验 → 解析分块 → 嵌入存储 → 检索与压缩 → 模型回答 → 返回来源引用。图谱和 Brain 是知识组织视图，不绕过文档所有权。

## 6. 部署拓扑

- Web：TanStack Start SSR 构建，部署至支持 Node SSR 的平台。
- API：独立 Node 服务，持有服务端变量并连接 Supabase、AI 和外部服务。
- 数据：Supabase 托管 PostgreSQL/Auth。
- Native：`apps/desktop` 中的 Tauri 加载 `apps/web/dist-native/client`，通过 HTTPS/WSS 访问远端 API。

生产环境必须使用 HTTPS/WSS；Web 与 API 可分离部署，但 CORS 只允许精确来源。

## 7. 架构决策记录

| ADR     | 背景                            | 决定                                         | 理由                             | 代价                          | 状态   |
| ------- | ------------------------------- | -------------------------------------------- | -------------------------------- | ----------------------------- | ------ |
| ADR-001 | 多套 Agent 写链路会导致状态分叉 | 新会话只写 `agent-v3`                        | 统一恢复、评分与事件语义         | 旧会话需要兼容读取            | 已采纳 |
| ADR-002 | 文字与语音体验目标不同          | 文字固定 coaching，语音固定 simulation       | 避免客户端任意组合造成不可测行为 | 模式扩展需新增产品决策        | 已采纳 |
| ADR-003 | Checkpoint 不适合作为业务数据库 | 业务表为事实源，Checkpoint 只恢复            | 支持审计、查询和独立重建         | 写入流程需要明确一致性        | 已采纳 |
| ADR-004 | SSE 需要断线重放                | 使用最小化 `agent_events` 和游标             | 避免重放完整敏感正文             | 事件 schema 必须稳定          | 已采纳 |
| ADR-005 | Web 与桌面端共享业务逻辑        | Native SPA + Tauri + 平台适配层              | 最大化 React feature 复用        | 需维护 WebView 平台差异       | 已采纳 |
| ADR-006 | API Key 属于高敏感数据          | 服务端 AES-256-GCM 加密保存                  | 降低数据库泄露影响               | 需要安全管理 `ENCRYPTION_KEY` | 已采纳 |
| ADR-007 | 迁移历史存在环境漂移风险        | 只新增迁移，治理前禁止全量 push/reset/repair | 避免破坏远端真实历史             | 发布需人工核验缺失能力        | 已采纳 |
| ADR-008 | 公开网页可被注入和污染          | 网页只作为受控证据，不作为指令               | 降低 Prompt 注入和错误归因       | 研究结果可能被拒绝或降级      | 已采纳 |
| ADR-009 | 占位节点与自由 Planner 导致链路漂移 | 独立准备工作流 + `interactive-v2` 精简 Graph | 让每个节点对应真实工作并稳定恢复 | 需保留旧 namespace 兼容      | 已采纳 |

ADR 状态变化必须在同一提交更新本表和相关设计文档。

## 8. 已知约束

- 没有可运行的 Redis/BullMQ generation Worker；不得按旧方案部署。
- Checkpoint 生产可用性依赖显式 schema 初始化和 PostgreSQL 连通性。
- OpenAPI 当前文档是筛选后的实际接口集合，旧 `/api/voice/*` HTTP 定义不得作为当前契约。
- Supabase migration history 未治理前，自动化数据库发布受限。
