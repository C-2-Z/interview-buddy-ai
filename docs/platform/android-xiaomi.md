# AI 面试模拟器 Android 客户端技术方案（小米优先）

## 1. 文档目标

本文档用于确定 AI 面试模拟器 Android 客户端的技术路线、架构边界、首版范围、兼容策略、发布流程与验收标准。

Android 端优先适配小米、Redmi 及 HyperOS/MIUI 设备。第一阶段以可安装的签名 APK 进行真机内测，稳定后再进入小米应用商店发布流程。

本文档仅描述技术方案，不包含具体代码实现。

## 2. 项目现状

当前项目已经具备以下跨端基础：

- Web 端使用 TanStack React Start、React 19、TanStack Router、Tailwind CSS 4。
- Windows 桌面端使用 Tauri 2，复用 Web 前端业务代码。
- 已存在面向 Native WebView 的静态 SPA 构建，产物输出到 `dist-native`。
- 已存在跨端运行时配置，可为 Native 构建指定独立的 HTTPS API 地址。
- 已存在平台适配层，用于统一认证存储、WebSocket、麦克风、音频、全屏和屏幕常亮等能力。
- Tauri Rust 入口已经具备移动端入口声明。
- 后端 Hono API、Supabase Auth、数据库和 AI Provider 均独立部署，客户端不需要内嵌服务端运行时。

因此，Android 端不需要重新开发一套业务应用，主要工作是补齐 Android 容器、平台能力适配、移动端交互、小米设备兼容和发布体系。

## 3. 建设目标与首版范围

### 3.1 建设目标

- 最大化复用现有 Web 和 Windows 端业务代码。
- 在小米主流设备上稳定完成一次完整的文本或语音模拟面试。
- 保持服务端 API、数据库和 AI Provider 架构不变。
- Android 特有能力通过明确的平台边界实现，避免平台判断散落在业务模块中。
- 首版完成可签名、可安装、可测试、可迭代的 APK，并预留应用商店发布能力。

### 3.2 Android v1 功能范围

首版包含：

- 邮箱密码登录、注册、会话恢复和退出登录。
- 面试入口、岗位与难度选择、岗位需求描述。
- 文本面试、追问、评分和综合报告。
- 语音面试、麦克风校准、实时连接和异常恢复。
- 历史记录、题库和题目详情。
- AI Provider、模型和用户 API Key 设置。
- 网络异常、权限异常和会话恢复提示。

首版不包含：

- 离线面试或端侧 AI 推理。
- 后台持续录音、后台面试或常驻前台服务。
- 小米推送、面试提醒和营销通知。
- 支付、订阅和应用内购买。
- 应用内热更新或绕过商店的可执行代码更新。
- 平板专用双栏布局和横屏深度适配。

## 4. 技术路线选型

### 4.1 方案对比

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| Tauri 2 Android | 复用现有 Tauri 工程、Native SPA 和平台适配层；包体相对较小；可共享 Windows 端基础设施 | Android 插件生态不如 Capacitor 完整，个别能力可能需要 Kotlin 插件 | 推荐 |
| Capacitor Android | Android 插件生态成熟，资料丰富 | 项目将同时维护 Tauri 和 Capacitor 两套 Native 容器、配置与生命周期模型 | 不采用 |
| React Native | 移动端生态成熟，原生交互能力强 | UI、路由、状态管理和业务页面需要大量重写 | 暂不采用 |
| 原生 Kotlin + Compose | 系统能力与性能控制最佳 | 开发成本最高，无法直接复用现有 React UI | 暂不采用 |

### 4.2 推荐结论

Android 客户端采用 **Tauri 2 Android + 现有 React Native SPA**。

选择该路线的核心原因不是单纯追求技术统一，而是项目已经完成了 Native SPA、运行时配置、Tauri Windows 容器和平台适配边界。继续使用 Tauri 能够把主要投入集中在 Android 真实差异上，而不是重新搭建第二套客户端架构。

正式实施前，应使用当时可用的官方文档重新确认 Tauri Android、Android Gradle Plugin、目标 SDK 和小米应用商店的最新要求，避免将本文档中的阶段性版本假设固化为长期约束。

## 5. 总体架构

```text
React 19 / TanStack Router / React Query / Tailwind
                         │
                  Native SPA 构建
                         │
                shared/platform 适配层
                 ┌───────┴────────┐
          Tauri Windows      Tauri Android
                                  │
                     Android 原生能力与插件
                                  │
                   HTTPS API / WSS 语音连接
                                  │
             Hono API + Supabase + AI Provider
```

架构遵循以下原则：

- 业务 feature、API 类型、认证流程和面试状态机由三端共享。
- Web SSR 构建和 Native SPA 构建继续保持独立，Android 不依赖 SSR 服务渲染页面。
- Android 只访问公开的 Hono API 和 Supabase 公共接口，不直接持有服务端密钥。
- 用户自定义 AI API Key 继续由后端加密存储，不能写入 APK 或 Android 本地配置。
- Android 专有能力统一收口到平台适配层或独立移动端 feature。
- 应用不依赖 Google Play Services，以保证小米国行设备正常使用。

## 6. Android 工程与构建方案

### 6.1 工程结构

- 使用 Tauri CLI 在现有 `src-tauri` 工程下生成 Android 工程。
- Android 应用 ID 沿用 `com.ezmock.interview-buddy`，避免后续签名、深链和商店身份不一致。
- Android 自动生成目录只承载 Gradle、Manifest、资源和必要的 Kotlin 原生桥接代码。
- 跨端业务仍保留在 `src/features`；Android 专属前端能力建立独立 feature，不混入已有业务域。

### 6.2 系统版本与架构

- 建议最低支持 Android 9（API 28），覆盖仍有实际使用价值的 MIUI/Redmi 设备，同时降低旧系统兼容成本。
- Target SDK 在实施时采用小米应用商店与 Android 官方要求的当前稳定版本。
- 内测真机包优先输出 `arm64-v8a`。
- 只有在需要 Android 模拟器测试时才额外输出 `x86_64`，避免无意义扩大正式包体。

### 6.3 环境配置

- Android 开发构建连接可访问的开发 API，不能使用手机无法访问的 `localhost`。
- Android 生产构建必须使用 HTTPS API 与 WSS 语音连接。
- 正式构建前执行 Native Bundle 校验，检查开发地址、明文 HTTP、缺失环境变量和敏感信息。
- 测试、预发布和生产环境分别配置，不允许通过修改源码切换服务地址。

### 6.4 签名管理

- 创建独立 Android release keystore，并制定离线备份与交接规则。
- keystore 文件、别名和密码不得提交到 Git。
- 本地通过受控环境变量或私有配置注入，CI 通过 Secret 注入。
- 内测 APK 和商店正式包使用同一正式签名，避免测试用户后续无法覆盖升级。
- 每次发布同时保存版本号、versionCode、构建产物摘要和签名证书指纹。

## 7. 平台适配设计

### 7.1 平台识别

当前 Native 目标同时服务 Windows 和未来 Android。实施时应将“构建目标”和“运行平台”分开表达：

- 构建目标用于区分 Web SSR 与 Native SPA。
- 运行平台用于区分浏览器、Tauri Windows 和 Tauri Android。

业务组件不应直接读取 User-Agent 或调用 Tauri 内部变量，而应通过平台适配接口获取能力。

### 7.2 认证与安全存储

- Supabase access token 和 refresh token 在 Android 上使用由 Android Keystore 保护的安全存储。
- 普通 UI 偏好可以保留在 WebView 本地存储，但认证令牌、敏感配置和用户 API Key 不得明文保存。
- 应用升级时应设计一次性会话迁移；迁移失败时安全退出登录，不允许进入半登录状态。
- Android 深链建议使用 `com.ezmock.interview-buddy://auth/callback`，并加入 Supabase Redirect URL 白名单。
- 深链回调必须校验协议、路径和认证参数，拒绝非预期跳转。

### 7.3 网络能力

- REST API 继续通过统一 HTTP Client 添加 Supabase Bearer Token。
- 语音面试继续使用 WSS，生产环境拒绝非加密连接。
- 监听 Android 网络状态，区分无网络、连接中、服务端错误和认证失效。
- 文本回答提交应带已有业务幂等标识，避免弱网重试造成重复回答。
- WebSocket 重连采用有限次数指数退避；超过阈值后由用户主动重试，避免后台无限耗电。
- 应用从后台恢复后重新验证 access token 和面试会话状态，再决定继续或跳转到恢复页面。

### 7.4 返回键与导航

- 普通二级页面按系统返回键回到上一页。
- 登录后的根页面首次返回提示“再次返回退出”，短时间内第二次返回才退出应用。
- 文本或语音面试进行中按返回键必须弹出退出确认，避免误触丢失进度。
- 弹窗、下拉菜单和全屏层优先消费返回事件，不能直接退出页面。
- Android 系统返回行为与页面内返回按钮保持一致。

### 7.5 生命周期

- 应用进入后台时停止或暂停麦克风采集，不允许无提示继续录音。
- 进入后台时释放不再需要的 AudioContext、屏幕常亮和临时音频资源。
- 语音连接根据面试状态安全断开或冻结，并记录可恢复状态。
- 回到前台时重新检查网络、麦克风权限、认证和服务端会话状态。
- 来电、其他应用抢占音频焦点或系统回收 WebView 后，应提供明确的恢复路径。

## 8. 语音面试方案

### 8.1 权限策略

- Manifest 仅声明实际需要的网络和麦克风权限。
- 不在应用首次启动时请求麦克风权限。
- 用户首次进入语音面试准备页时，先解释使用目的，再触发系统授权。
- 用户拒绝后允许继续使用文本面试。
- 用户选择“不再询问”后展示前往系统设置的入口，不循环弹出授权框。
- 首版不申请电话、通讯录、精确位置、存储目录或后台录音权限。

### 8.2 音频流程

- 进入准备页后进行麦克风存在性、权限、采集和播放校准。
- 语音面试开始后保持屏幕常亮，结束、退出或异常中断时立即释放。
- 接入 Android 音频焦点管理，处理来电、闹钟、音乐播放器和蓝牙设备切换。
- 蓝牙耳机不是首版发布阻断条件，但必须保证切换失败时不会导致应用崩溃或无限重连。
- 页面持续展示麦克风状态、录音状态、网络状态和 AI 响应状态。

### 8.3 异常恢复

- 麦克风权限被系统撤销时立即停止采集并给出恢复说明。
- 短暂断网时保留当前问题和已输入内容，尝试有限次数重连。
- 长时间断网或服务端会话已结束时，跳转到可恢复页面或报告页面。
- 应用被系统杀死后再次打开，应依据服务端状态恢复未完成会话，不依赖内存状态猜测。
- 所有恢复动作必须避免重复提交回答或重复生成评分。

## 9. 移动端 UI 与交互

### 9.1 导航与布局

- 手机端主导航建议采用底部导航，包含首页、题库、历史和设置等高频入口。
- 创建面试和面试会话使用沉浸式页面，隐藏常规导航，减少误操作。
- 页面适配全面屏安全区、挖孔区域、手势导航条和软键盘。
- 软键盘弹出时保证当前问题、输入框和提交按钮仍可访问。
- 横屏首版只保证不崩溃和内容可操作，不单独设计横屏信息架构。

### 9.2 可用性要求

- 关键触控区域不小于 44×44 CSS px。
- 不依赖 hover 才能发现或触发重要操作。
- 长文本报告支持平滑滚动、复制和清晰的章节层级。
- 加载、断网、重连、权限拒绝和服务端错误必须使用用户可理解的中文提示。
- 适配系统字体放大，核心按钮不能因字体放大而不可点击。
- 深色模式首版沿用应用现有主题，不强制接入 HyperOS 动态取色。

## 10. 小米与 HyperOS 专项兼容

### 10.1 主要风险

- 不同 HyperOS/MIUI 版本对后台进程、WebView、麦克风和电池策略处理不同。
- 用户可能关闭麦克风权限、后台网络或应用自启动权限。
- 部分旧设备的系统 WebView 版本较低，可能影响媒体 API、WebSocket 或 CSS 表现。
- 系统省电策略可能在锁屏或切后台后中断语音连接。
- 国内设备通常没有完整 Google 服务，任何隐式依赖都可能造成运行失败。

### 10.2 处理原则

- 不将关闭电池优化、自启动或后台运行权限设为应用启动前置条件。
- 首版不承诺后台语音面试，切后台即进入可解释、可恢复的暂停流程。
- 仅在真机证明确有必要时，提供小米系统设置引导，并解释原因和影响。
- 检测到 WebView 能力不足时展示升级系统 WebView 或系统组件的明确提示。
- 不接入依赖 Google Play Services 的认证、推送、地图或分析 SDK。
- 若二期需要通知，单独设计统一设备令牌模块并接入 Mi Push，不直接把推送逻辑塞入面试模块。

### 10.3 真机测试矩阵

至少覆盖以下三类设备：

| 设备类型 | 建议范围 | 主要验证内容 |
| --- | --- | --- |
| 小米旗舰或次旗舰 | 较新 HyperOS、Android 当前主流版本 | 全功能、性能、权限和语音稳定性 |
| Redmi 中端机 | 主流 HyperOS/MIUI、有限内存 | WebView 性能、页面滚动、内存回收和弱网恢复 |
| 较旧小米设备 | Android 9～11 范围内可获得设备 | 最低系统兼容、旧 WebView 和字体布局 |

## 11. 安全与隐私

- APK 中不得包含 DeepSeek、OpenAI、Anthropic、Supabase Service Role 或其他服务端密钥。
- 用户 API Key 仍由服务端 AES-256-GCM 加密存储，Android 端不持久化明文。
- 客户端日志不得记录 access token、refresh token、Authorization、API Key、完整语音数据或敏感回答。
- 仅允许访问白名单中的 API、Supabase 和必要外部链接。
- 外部隐私政策、用户协议和帮助链接通过系统浏览器打开。
- 麦克风权限用途必须与实际语音面试功能一致，不得用于后台采集。
- 账号注销入口、数据处理说明和隐私政策必须在应用内可发现。
- 上架前完成第三方 SDK 清单、个人信息收集清单和权限用途说明。

## 12. 发布与合规方案

### 12.1 内测发布

- 第一阶段输出正式签名的 release APK。
- 通过受控渠道发给测试人员，不公开传播未完成合规审查的安装包。
- 每个测试包使用唯一递增 versionCode，并记录对应 Git 提交和环境。
- 收集设备型号、系统版本、WebView 版本、复现步骤和脱敏日志。

### 12.2 小米应用商店

进入小米应用商店前应完成：

- 小米开放平台开发者主体认证。
- 应用名称、图标、截图、简介、分类和联系方式。
- 隐私政策与用户协议的公网 HTTPS 页面。
- 软件著作权或商店当时要求的权属材料。
- 中国大陆移动互联网应用程序备案及相关信息展示。
- 权限使用说明、第三方 SDK 清单、个人信息收集与共享清单。
- 测试账号及审核人员可完整体验的操作说明。
- 账号注销与用户数据删除流程。

小米平台规则、Android Target SDK 和备案材料要求可能变化，正式提交前必须按当时官方要求复核。

## 13. 测试方案

### 13.1 自动化测试

- 平台识别与构建目标解析。
- API、WebSocket 和认证回调地址解析。
- Android 安全存储读写、迁移和清理。
- 网络状态变化与有限重连策略。
- 前后台生命周期和面试状态迁移。
- 返回键、退出确认和弹层优先级。
- 权限状态到 UI 状态的映射。

### 13.2 集成与真机测试

- 注册、登录、自动恢复会话和退出登录。
- 创建文本面试、连续回答、评分和生成报告。
- 创建语音面试、首次授权、采集、追问和结束面试。
- 历史记录、题库、设置和用户 API Key 配置。
- 麦克风允许、拒绝、永久拒绝和系统撤销。
- Wi-Fi 与移动网络切换、短暂断网、长时间断网和服务端超时。
- 切后台、锁屏、来电、音频焦点抢占和应用被系统回收。
- 软键盘、全面屏安全区、字体放大、深色模式和长报告滚动。
- 安装、覆盖升级、退出重登和卸载后重装。

### 13.3 发布验收标准

- 三类小米真机均能安装、启动、登录和退出。
- 每台设备至少完整完成一次文本面试。
- 支持语音的设备至少完整完成一次语音面试。
- 弱网和前后台切换不会造成重复回答、重复评分或不可恢复白屏。
- 永久拒绝麦克风权限后仍可正常使用文本面试。
- release APK 不包含服务端密钥、开发地址或签名密码。
- Web、Windows 和 Android 的共享业务流程没有明显功能回归。
- 前端、API、Native Bundle 和 Android release 构建验证全部通过。

## 14. 分阶段实施计划

### 阶段一：Android 基础壳层

- 初始化 Tauri Android 工程和构建链路。
- 跑通 Native SPA、生产 API、Supabase Auth 和基础导航。
- 建立签名、版本号和构建产物管理规则。

交付物：可安装、可登录、可访问核心页面的签名 APK。

### 阶段二：文本核心闭环

- 完成首页、创建面试、文本会话、历史、报告、题库和设置的小屏适配。
- 补齐返回键、软键盘、安全区、网络错误和状态恢复。

交付物：可在小米真机完成完整文本面试的 APK。

### 阶段三：语音能力

- 接入麦克风权限、音频焦点、屏幕常亮和生命周期管理。
- 完成 WSS 重连、异常恢复和语音状态提示。

交付物：可在前台稳定完成语音面试的 APK。

### 阶段四：小米专项验证

- 执行 HyperOS/MIUI 真机矩阵。
- 验证权限、弱网、锁屏、后台、旧 WebView、内存和耗电表现。
- 修复阻断问题并完成回归测试。

交付物：满足内部发布验收标准的候选版本。

### 阶段五：商店发布准备

- 完成隐私、备案、软著、截图、测试账号和审核说明。
- 输出商店包并执行签名与安全复核。

交付物：可提交小米应用商店审核的正式版本。

## 15. 主要风险与应对

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| Tauri Android 插件缺少所需能力 | 阻塞安全存储、权限或生命周期功能 | 优先使用官方插件；缺失能力通过小型 Kotlin 插件补齐，不改变业务层接口 |
| WebView 媒体能力在部分小米设备表现不一致 | 语音面试不可用或不稳定 | 在准备页执行能力检测；保留文本面试降级入口；建立真机矩阵 |
| HyperOS 后台限制中断语音 | 切后台后连接丢失 | 明确仅支持前台语音；后台暂停并在前台执行恢复流程 |
| Native SPA 与 SSR 行为差异 | 路由、认证回调或刷新异常 | Native 构建独立验证所有入口和深链，不依赖 SSR fallback |
| 应用商店规则变化 | 上架延期 | 内测与商店材料并行准备；提交前按官方规则复核 |
| 签名密钥丢失 | 无法覆盖升级 | 离线双份备份、明确保管责任、CI Secret 和证书指纹留档 |

## 16. 后续可选能力

以下能力不属于 v1，应在核心闭环稳定后单独立项：

- Mi Push 面试提醒与结果通知。
- Android 平板和折叠屏布局。
- 蓝牙耳机深度优化和音频路由选择。
- 应用内版本提示与商店更新跳转。
- 崩溃分析、性能监控和经隐私审查的产品分析。
- 多应用商店发布，包括华为、OPPO、vivo 和应用宝。

## 17. 最终建议

项目应采用 Tauri 2 Android 延伸现有跨端架构，避免引入第二套 Native 容器。实施顺序应先确保 Android 基础壳层和文本面试稳定，再接入语音与小米专项能力，最后处理商店发布。

首个里程碑不应以“成功打出 APK”为完成标准，而应以“在至少三类小米真机上完成完整文本面试，并能安全处理登录、弱网、返回键和应用恢复”为标准。语音面试通过独立阶段进入发布门禁，以控制首版风险。
